# Seed-based color generation

Rem's public API lives in `dev.rem.api`. MCU types are implementation details
and are not part of the public method signatures or returned values.

## API behavior

`Argb` stores a 32-bit `0xAARRGGBB` value. Use `Argb.fromLong` for unsigned
hex literals, or `Argb.fromInt` when the value is already a signed Kotlin
`Int`. The alpha channel on a seed is ignored: MCU receives the seed's RGB
channels with alpha forced to `0xFF`. Generated semantic role colors are
opaque ARGB values.

`Rem.createScheme(seed, mode, options)` generates exactly one light or dark
scheme, selected explicitly with `ThemeMode.LIGHT` or `ThemeMode.DARK`.
`Rem.createSchemes(seed, options)` generates both modes using the same style,
seed, and contrast level, returning `ThemeSchemes.light` and `.dark`.

`SchemeOptions.contrastLevel` is finite and inclusive from `-1.0` to `1.0`;
zero is the standard contrast setting. Values outside the range, NaN, and
infinities throw `IllegalArgumentException`. This parameter is passed to MCU's
dynamic scheme generator. It is a contrast preference, not a promise that every
foreground/background pair meets a particular accessibility ratio.

Rem explicitly selects MCU's `SPEC_2025` color specification for every
generation call. Output stability is expected for identical inputs and the
same Rem/MCU versions; changes in MCU, specification, or Rem's mappings can
change generated values.

## Theme styles

The initial supported `ThemeStyle` values map directly to MCU 6.0.0 scheme
classes:

| Rem style | MCU variant | Description |
| --- | --- | --- |
| `TONAL_SPOT` | `SchemeTonalSpot` | Balanced, restrained tonal palettes; default. |
| `FIDELITY` | `SchemeFidelity` | Keeps palette hues and tones close to the source color. |
| `CONTENT` | `SchemeContent` | Content-derived palette behavior. |
| `EXPRESSIVE` | `SchemeExpressive` | More varied palette relationships. |
| `MONOCHROME` | `SchemeMonochrome` | Neutral monochrome palette. |
| `VIBRANT` | `SchemeVibrant` | Higher-chroma palette behavior. |

These names identify MCU variants rather than additional Rem algorithms.
CMF and experimental variants are not exposed.

## Color roles and Material 3 compatibility

`ColorScheme` exposes the 48 roles in the current AndroidX Material 3
`ColorScheme` constructor. It is a Rem-owned, UI-framework-independent value
model made from concrete opaque ARGB values, not an AndroidX or Compose type.
The names intentionally follow Material 3 so a future adapter can map the
roles without making `rem-core` depend on presentation APIs.

The compatibility baseline is AndroidX's current Material 3 `ColorScheme`
property/constructor set (see the [API reference](https://developer.android.com/reference/kotlin/androidx/compose/material3/ColorScheme)
and [AndroidX source](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/ColorScheme.kt)).
Material 3 deprecates older constructor overloads that omit newer role groups;
the current API still lists roles such as `background` and `surfaceVariant`.
Rem includes those currently listed roles while excluding constructor-history
compatibility behavior.

All roles are required and directly generated by MCU 6.0.0:

- **Accent roles:** each of `primary`, `secondary`, and `tertiary` has a base
  color, matching `on*` color, a container and its `on*` color. `primary`
  additionally has `inversePrimary`. Each accent family has `*Fixed`,
  `*FixedDim`, `on*Fixed`, and `on*FixedVariant` roles. Fixed colors are
  intended to retain their tone across light and dark schemes.
- **Error roles:** `error`, `onError`, `errorContainer`, `onErrorContainer`.
- **Background and surface roles:** `background`, `onBackground`, `surface`,
  `onSurface`, `surfaceVariant`, `onSurfaceVariant`, `surfaceTint`,
  `inverseSurface`, `inverseOnSurface`, `surfaceBright`, `surfaceDim`,
  `surfaceContainer`, `surfaceContainerHigh`, `surfaceContainerHighest`,
  `surfaceContainerLow`, and `surfaceContainerLowest`.
- **Utility roles:** `outline`, `outlineVariant`, and `scrim`.

The Material 3 API also has older `ColorScheme` constructor overloads that are
deprecated because they omit newer surface-container or fixed-color roles.
Rem models the complete current constructor role set and does not expose those
older overloads. Names such as `background`, `onBackground`, `surfaceVariant`,
and `onSurfaceVariant` remain properties in that current role set; Rem keeps
them for direct compatibility rather than silently renaming them. Role
meanings follow Material 3: `on*` values are intended for content over the
matching role, container roles provide tonal container colors, fixed roles
retain tones across modes, inverse roles support contrasting contexts, and
surface container roles provide ordered surface emphasis. No role needs
derivation or substitution in this model.

`rem-core` does not convert to Compose `ColorScheme` automatically. A future
UI adapter can perform that boundary conversion without bringing Compose,
Android UI, or platform presentation dependencies into the core.

## Extracting a seed from image pixels

`Rem.extractSeedColor(pixels)` accepts decoded pixels as `IntArray` entries in
`0xAARRGGBB` format. When sourced from an image, provide the pixels in
row-major order. Rem accepts the flat array and does not require dimensions,
load files, or decode images; image decoding and any resizing are the caller's
responsibility.

```kotlin
// `decodedPixels` is supplied by the application's platform image decoder.
val seed = Rem.extractSeedColor(decodedPixels)
val lightAndDark = Rem.createSchemes(seed)
```

Pixels with alpha `0x00` are removed before quantization so hidden RGB values
cannot affect the result. Any nonzero-alpha pixel is retained and normalized
to opaque using its RGB channels. MCU's quantizer converts RGB to Lab and does
not composite or weight by alpha. Since Rem has no knowledge of the eventual
background, partially transparent pixels contribute their uncomposited RGB
at full pixel weight; this policy is deterministic and avoids assuming a
white, black, or other compositing color. Pixels with the same RGB therefore
contribute together even when their input alpha differs.

Empty and all-transparent inputs throw `IllegalArgumentException`. Rem passes
the visible opaque pixels through MCU `QuantizerCelebi.quantize` with
`maxColors = 128`, MCU's documented reasonable default. It then calls
`Score.score` with its default filtering enabled, `desired = 1`, and
`fallbackColorArgb = null`. The first returned color is the highest-ranked
eligible seed. When scoring finds no eligible color, Rem throws
`IllegalArgumentException` instead of returning MCU's generic Google Blue
fallback, which would be unrelated to the supplied pixels.

MCU's Wsmeans quantizer uses a fixed internal random seed. Repeated calls with
the same ordered input and the same MCU version therefore produce the same
seed. Rem does not promise the same output across dependency upgrades or
different pixel orderings.

## Limitations

- Rem extracts seeds from decoded pixel arrays only; it does not decode or
  resize image files.
- Rem is UI-framework independent and does not include Compose adapters.
- The role model follows the current AndroidX Material 3 `ColorScheme` role
  set; it does not promise compatibility with every framework-specific API or
  deprecated constructor overload.
- MCU is a third-party dependency. Its Kotlin Multiplatform target metadata and
  licensing review are recorded in [dependency-review.md](dependency-review.md)
  and [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).
